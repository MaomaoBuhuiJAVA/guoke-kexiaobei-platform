# 科小贝轻量部署规则

## 固定流程

1. 代码先提交到 `main`，由 GitHub Actions 在 Ubuntu 24.04、Node.js 22 环境中执行 `npm ci`、测试、TypeScript 检查和生产构建。
2. 构建产物必须来自 Linux 环境，生成 `.next/standalone`、`.next/static`、`public` 和运行所需 package 文件的压缩包，并记录 Git commit SHA。
3. ECS 只接收已经构建好的 Linux 部署包，解压到新的 `/opt/guoke/releases/<release>` 目录，完成候选版本验收后切换 `/opt/guoke/current` 并重启 `guoke-web`。
4. ECS 不执行 `npm run build`、`npm ci` 或大型依赖安装。这样可以避免在 1.7GB 内存的服务器上构建导致资源耗尽、SSH 失联和半成品发布。
5. 数据库迁移必须单独评审和执行；普通前端或服务代码发布不得自动修改数据库。
6. 发布完成后验证 `guoke-web`、Nginx、PostgreSQL、首页、`/lab`、`/games` 和本次变更涉及的 API。必须检查 HTML 引用的 CSS、JS、图片及浏览器实际显示、交互，不能仅凭页面返回 200 判定成功；失败立即回滚。保留上一版本用于回滚。

## 构建产物要求

- 不得上传 Windows 的 `node_modules` 或指向本机盘符的符号链接。
- Prisma Client、Sharp 等原生依赖必须在 Linux 构建环境中生成。
- 运行时环境变量只保存在 ECS 的 `/etc/guoke/*.env`，不进入 GitHub artifact。
- 每个发布包必须带 `BUILD_COMMIT` 和 `BUILD_TIME`，上线记录写入 `docs/releases/` 并推送 GitHub。
- 服务入口是 `.next/standalone/server.js`，运行目录内必须有 `.next/standalone/.next/static`、`.next/standalone/public` 和 `.next/standalone/.next/cache`。根目录的同名资源不代替运行目录资源。
- 组装后必须运行 `node scripts/verify-standalone-package.mjs ../deploy-package`，逐文件校验静态资源完整性，失败不允许上传发布包。
