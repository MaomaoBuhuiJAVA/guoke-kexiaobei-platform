# 网站维护保底页

## 故障时的行为

Nginx 独立提供维护页。Next.js 服务停机、连接失败或网页返回 500、502、503、504 时，网页请求显示“网站正在维护更新中”，HTTP 状态为 503，并带 `Retry-After: 60`、禁止缓存及禁止搜索索引的响应头。点击“重新尝试”会重新加载原网址，保留路径和查询参数；服务恢复后正常访问应用。

`/api/` 请求仍转发应用并保留业务状态码与 JSON 正文，已有登录/注册的精确路由、限流、请求大小和代理超时保持原配置。维护页不依赖 Next.js、数据库、外部图片、字体、CSS 或 JavaScript 文件。

整台 ECS、Nginx、域名解析、TLS 或访问者网络失效时，此页无法显示；覆盖这类故障需要另外部署外部节点或 CDN。已加载页面中的局部接口失败仍由应用现有错误提示处理。

## 文件

- `ops/nginx/maintenance.html`：静态页面，安装至 `/var/www/guoke-maintenance/index.html`。
- `ops/nginx/maintenance.conf`：Nginx 内部错误页面，安装至 `/etc/nginx/snippets/guoke-maintenance.conf`。
- `ops/nginx/configure_maintenance.py`：对现有 Nginx 站点做增量配置；遇到未知结构停止，不覆盖已有 API 精确路由。
- `ops/nginx/deploy.py`：默认只预览差异；`--apply` 才安装文件和 reload Nginx。持有共享发布锁、校验原站点哈希、备份原文件，并在检查失败时恢复。
- `ops/nginx/test_maintenance.py`：启动独立临时 Nginx 和合成 HTTP 服务，验证故障页、API 状态保留、后端停机及恢复、精确路由、禁止直接访问内部错误页。不会停止或重启正式服务。

## 构建和部署

`.github/workflows/maintenance-pages.yml` 在 GitHub Actions Ubuntu 环境中运行真实 Nginx 集成测试，生成 `nginx-maintenance-<commit>` artifact。静态文件部署无需构建或重启 Next.js；生产 ECS 禁止安装构建依赖。

下载 GitHub artifact，将其中 `maintenance-package.tar.gz` 解压至服务器私有暂存目录，先校验 SHA-256 清单，再预览配置差异：

```bash
sha256sum -c SHA256SUMS
python3 ops/nginx/deploy.py --expected-site-sha256 <刚核实的站点配置哈希>
python3 ops/nginx/deploy.py --expected-site-sha256 <相同配置哈希> --apply
```

部署前原站点哈希由 `sha256sum /etc/nginx/sites-available/guoke` 获取。脚本只变更 Nginx 与维护页文件，执行 `nginx -t` 和 `systemctl reload nginx`；不修改数据库、应用 release 或 `guoke-web` 服务。配置备份和部署记录保存在 `/var/backups/guoke/nginx-maintenance/`。

部署后检查首页、资源库、游戏页及其 CSS/JS，确认正常路由没有被错误拦截。故障模拟仅在独立端口进行，禁止通过停止生产服务做验收。
